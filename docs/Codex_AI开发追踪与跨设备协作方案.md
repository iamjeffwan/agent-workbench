# Codex AI 开发追踪与跨设备协作方案

## 一、现在的个人版本

当前不需要强求 Codex 的 `session`（会话）跨设备同步。

更实际的方式，是把项目状态拆成三部分：

- Git：保存代码、配置、流程文档等正式产物。
- `JSONL`（JSON 行式）：记录 Codex 每轮对话、工具调用、请求、响应和操作过程。
- 流程文档：把某次开发过程整理成可读的状态说明，包括做了什么、为什么这样做、现在到哪一步、下一步是什么。

办公室电脑完成一轮开发后，把代码、流程文档以及需要保留的行为记录同步到 Git。家里的电脑拉取最新仓库后，新开一个 Codex `session`（会话），读取这些内容，就能继续开发。

所以真正需要跨设备同步的不是原始 `session`（会话），而是“项目状态和开发过程”。

## 二、`JSONL`（JSON 行式）的定位

`JSONL`（JSON 行式）不是主要用来恢复 Codex 原始会话的，它更适合作为底层行为记录。

它可以用于：

- 查看 Codex 每轮具体做了什么；
- 回溯请求、响应和工具调用；
- 查看操作顺序；
- 生成流程文档；
- 调试某次开发过程；
- 分析 Agent（智能代理）的行为；
- 为后续统计和审计提供原始数据。

你现在的工作台，本质上是在把这些底层事件转成更容易理解的开发过程。

## 三、跨设备怎么做

个人阶段最简单的是 Git。

办公室电脑：

1. Codex 完成开发。
2. 工作台读取本机 `JSONL`（JSON 行式）。
3. 生成或更新流程文档。
4. 在工作台中把任务加入 `Sync`（同步），生成项目内的脱敏任务证据。
5. 查看整个项目的变更清单，确认后提交代码、流程文档和同步数据。
6. 推送到远程 Git 仓库。

家里电脑：

1. 拉取最新仓库。
2. 工作台读取项目内的同步任务。
3. 在 `View`（查看）中打开 `Sync`（同步）任务，查看办公室电脑中发生过的 Codex 操作。
4. 新开 Codex `session`（会话）继续开发。

这样实现的是“开发上下文跨设备”，而不是“原始 Codex 会话跨设备”。

## 四、Git 和云服务的技术区别

Git 本质上是版本控制系统，擅长：

- 保存完整历史；
- 查看修改差异；
- 回退；
- 分支；
- 合并；
- 冲突处理；
- 跨设备同步代码和文档。

Git 本身是本地工具。GitHub、GitLab、Bitbucket、Gitea、Forgejo 等只是远程 Git 仓库的不同实现。

典型 Git 同步是：

`commit`（提交）→ `push`（推送）→ 另一端 `pull`（拉取）。

工作台的便捷方案仍然操作当前项目的整个仓库：拉取使用安全的快进方式；提交前展示代码、文档和同步目录的变更；用户确认后再提交和推送。检测到未提交修改、分支分叉或冲突时停止，不自动暂存、合并、变基、重置或强制推送。GitHub 仓库创建和连接通过 `gh`（GitHub 命令行工具）完成，工作台不保存令牌。

脚本可以让它自动执行，所以也能做到比较频繁的同步，但 Git 的设计目标仍然不是实时事件系统。

云端后端更适合：

- 实时接收机器上传的数据；
- 多客户端同时在线；
- 服务器主动推送变化；
- 在线查询；
- 权限管理；
- 成员和组织管理；
- 统计聚合；
- 告警；
- 大量结构化日志。

所以可以简单理解：

- Git 更适合“历史状态和文件版本”。
- 云端后端更适合“当前状态和实时协作”。

## 五、为什么个人版先用 Git

如果目前是：

- 一个人；
- 两三台电脑；
- 主要目的是继续开发和回溯；
- 不要求秒级实时；
- 数据量不大；

那么 Git 基本已经够用。

当前个人版可以理解成：

**Codex + 本地行为追踪 + 流程文档 + Git。**

没有必要为了“云”而单独建设云服务。

## 六、以后的小团队版本

如果以后变成工作室或小公司使用，情况会不一样。

一个小团队可能只有几个人，却同时控制多个 Agent（智能代理）开发。人的主要工作逐渐变成：

- 提需求；
- 拆任务；
- 观察 Agent（智能代理）执行；
- 检查结果；
- 测试；
- 反馈；
- 调整；
- 验收。

这时候，现在的追踪系统就可以从“个人 Codex 日志工具”继续演进成团队协作平台。

## 七、团队版需要记录什么

每一次 AI 开发活动，都可以关联：

- 哪个成员发起；
- 使用哪个模型；
- 属于哪个项目；
- 属于哪个任务；
- 对应哪个 Codex `session`（会话）；
- Agent（智能代理）做了哪些操作；
- 调用了哪些工具；
- 修改了哪些文件；
- 最终对应哪些 Git 提交；
- 消耗多少 Token；
- 成本多少；
- 测试结果如何；
- 是否验收；
- 谁进行了确认。

这样，一次 AI 开发就不只是聊天记录，而是一条完整的开发活动记录。

## 八、团队版为什么会需要云端

多人以后，仅靠 Git 会逐渐不够。

不是因为 Git 不能存文件，而是团队会产生大量“文件之外的实时状态”，例如：

- 谁正在运行 Agent（智能代理）；
- 哪个任务正在执行；
- 哪个任务失败；
- 哪个 Agent（智能代理）调用异常；
- 今天每个人用了多少 Token；
- 每个项目花了多少模型成本；
- 哪个任务对应哪些 Git 提交；
- 某次开发是谁发起的；
- 谁能查看哪些项目；
- 某个任务是否已经验收。

这些数据更适合统一放到云端后端。

团队版可以逐渐形成：

**本地 Agent（智能代理）追踪器 + 云端数据服务 + Git 仓库 + Web 工作台。**

## 九、团队版可以发展的能力

### 1. 统一开发日志

按成员、项目、任务、模型、时间、Git 提交查看所有 Agent（智能代理）的开发过程。

### 2. 开发过程回溯

出现问题以后，可以看到：

- 当时输入了什么；
- Agent（智能代理）如何执行；
- 调用了什么；
- 修改了哪些文件；
- 为什么产生当前结果；
- 最终对应哪个提交。

Git 能告诉你“代码变了什么”。

行为追踪还能告诉你“为什么会这样改”。

### 3. 权限划分

可以逐渐加入：

- 项目权限；
- 成员权限；
- 管理员权限；
- 日志查看权限；
- 成本查看权限；
- 敏感项目隔离。

### 4. 责任划分

一条完整链路可以是：

成员 → 任务 → Agent（智能代理）→ 行为记录 → 流程文档 → Git 提交 → 测试 → 验收。

以后出现问题，就可以直接回溯，而不是靠聊天记录或口头解释。

### 5. Token 和成本统计

团队可以统计：

- 每个人 Token 消耗；
- 每个项目 Token 消耗；
- 每种模型消耗；
- 每个任务成本；
- 成功任务和失败任务成本；
- 单个功能平均 AI 开发成本。

这样 AI 开发成本就可以像服务器成本一样被管理。

## 十、产品定位

这个项目以后不必只理解成“Codex 日志查看器”。

更合适的方向是：

**面向 AI Agent（人工智能代理）开发团队的开发过程追踪与协作平台。**

Git 负责代码本身的版本历史。

平台负责 Git 不擅长的部分：

- AI 为什么这样改；
- 谁让 AI 做的；
- AI 做了哪些操作；
- 用了多少模型资源；
- 哪个任务对应哪些代码；
- 当前进行到哪里；
- 谁测试；
- 谁验收；
- 出现问题以后怎么回溯。

## 十一、演进路线

### 第一阶段：个人本地版

- 本地读取 Codex `JSONL`（JSON 行式）。
- 展示每轮对话和操作。
- 生成流程文档。
- 与项目代码关联。

### 第二阶段：个人跨设备版

- 代码进入 Git。
- 流程文档进入 Git。
- 需要保留的 `JSONL`（JSON 行式）同步到 Git。
- 多台设备通过远程仓库交换项目状态。
- 不追求原始 Codex `session`（会话）跨设备。

### 第三阶段：轻量团队版

- 多成员；
- 多项目；
- 多 Agent（智能代理）；
- 统一日志；
- Git 提交关联；
- 任务关联；
- 成本统计。

### 第四阶段：云端团队版

- 云端实时上传行为事件；
- Web 工作台；
- 实时任务状态；
- 权限系统；
- 团队管理；
- Token 和成本统计；
- 调试与回溯；
- 告警；
- 审计；
- 项目交接。

## 十二、最终理解

个人阶段，Git 已经可以解决：

**代码 + 文档 + 行为历史的跨设备同步。**

真正需要云端，是当系统从“个人开发记录”变成“团队共同运行的一套 AI 开发系统”以后。

到那时，云端解决的不只是文件存储，而是：

**实时状态、团队权限、统一日志、成本统计、责任追踪和协作管理。**

整条路线可以概括为：

**个人 Codex 行为追踪 → Git 跨设备开发记录 → 多人 Agent（智能代理）协作 → 云端 AI 开发管理平台。**

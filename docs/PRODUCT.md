# `Agent Workbench`（智能开发工作台）产品基线

> 状态：当前有效
> 更新日期：2026-08-15
> 本文整合 2026 年 8 月提交的两份新产品方案，作为后续产品规划与开发取舍的主要依据。

`docs/design-references`（设计参考目录）、`docs/research`（调研目录）和 `docs/task-flows`（任务流程目录）只提供设计、调研和历史任务证据，不决定产品方向。

## 1. 产品定位

这是一个面向真实软件开发的 `Codex`（代码代理）工程工作台：读取本地 `session JSONL`（会话事件文件），还原开发过程，形成可跨设备接续的项目状态；再基于真实证据发现结果问题、过程异常和深层工程风险，将可复用经验整理成优化候选，并验证这些优化是否真正减少返工、`Token`（令牌）和对高能力模型的依赖。

个人使用是当前重点。团队管理和本地算力属于后续扩展，不应干扰近期主线。

## 2. 产品原则

1. 只面向 `Codex`（代码代理）。`Cursor`（旧代码编辑器来源）不再属于产品方向。
2. `Codex session JSONL`（代码代理会话事件文件）是行为追踪的唯一原始来源；代码、测试、截图和文档是结果证据。
3. 原始记录、结构化事件和模型结论必须分开。任何审查结论都应能回到来源。
4. 跨设备延续的是项目状态，不是同一个会话。新设备可以开启新会话继续工作。
5. 审查只提出有证据的风险，不把模型意见当作判决。
6. 优化先生成候选，再由人确认是否采用；生成更多 `Skill`（技能）本身不是成功指标。
7. 优先复用 `Git`（版本控制）、成熟容器和调度方案，不重复建设已有基础设施。
8. 不要求记录或暴露模型的完整内部推理，只保留可审查的引用来源、决策依据摘要和执行结果。

## 3. 核心数据结构

产品内的数据按以下层级组织：

项目 → 任务 → 会话 → 轮次 → 事件 → 证据

- 项目：一个代码仓库或工作目录。
- 任务：用户希望完成的一项开发目标，可以选择一个或多个轮次作为范围。
- 会话：一次连续的代码代理对话。
- 轮次：一次用户输入及其触发的完整执行过程。
- 事件：轮次中的具体行为，例如回复、工具调用、命令执行、补丁应用或任务结束。
- 证据：事件产生或引用的内容，例如文件变化、测试结果、截图、工具输出、模型调用、耗时、令牌消耗及原始记录位置。

时间线主要展示事件。证据从对应事件进入查看，不与事件混成一批含义不清的平级日志。

## 4. 整体功能结构

### 4.1 执行观察与跨设备项目接续

读取会话事件文件中的对话、工具调用、命令执行、文件修改、耗时、令牌、状态和关键上下文，整理为统一 `Timeline`（时间线），并保留原始记录引用。

当前先实现确定性的结果审查：根据命令失败、测试失败、构建失败和结构化验证结果生成可回溯提示；不把代码代理的总结文字直接当作通过依据，也不在本阶段自动启动浏览器或调用独立审查模型。

任务结束后，根据所选轮次生成流程文档，记录任务目标、已完成内容、当前状态、关键决策、验证结果、遗留问题和下一步。代码、流程文档与必要追踪记录共同组成“项目状态”，通过当前项目仓库的 `Git`（版本控制）在设备之间同步。

用户手动把任务加入 `Sync`（同步）后，工作台将脱敏后的结构化事件写入项目内 `.agent-workbench-sync/tasks/<task-id>`（同步任务目录）。工作台提供整个项目仓库的拉取，以及展示变更后确认式提交和推送；已有 `GitHub`（代码托管平台）远程仓库时可直接使用，首次连接可通过 `gh`（GitHub 命令行工具）创建私有仓库。工作台不保存远程令牌，也不强制推送或自动解决冲突。

另一台设备拉取项目后，重新开启代码代理会话，优先读取最新代码和流程文档；只有需要深度回溯时，才读取历史会话事件文件。不要求恢复原会话。

原始会话文件默认不进入仓库，只同步脱敏后的任务证据。产品核心仍兼容不同远程 Git 仓库，GitHub 只作为便捷连接方式。

### 4.2 三层审查

第一层是结果审查，判断功能、测试、性能和视觉结果是否符合要求。当前实现先覆盖命令、测试、构建、`Lint`（代码检查）和结构化结果文件；界面任务可以由代码代理使用 `Playwright`（浏览器自动化工具）生成截图、断言和测量结果，再由工作台读取，不由工作台自动执行浏览器。当前结构化结果约定优先放在项目 `.agent-workbench/validation-result.json`，也接受 `test-results/agent-workbench-validation.json`。

第二层是过程异常识别，根据可观测信号发现长时间阻塞、重复调用、频繁返工、重复造轮子、上下文膨胀等模式。

第三层是独立高能力模型审查，从架构、边界、耦合、复杂度、可维护性、可测试性、性能和安全等角度提出风险假设。每项结论至少包含证据、风险、可能影响和验证建议。

### 4.3 优化生成

优化模型使用审查证据和项目上下文，判断问题是否值得沉淀，并生成以下候选：

- `Skill`（技能）或项目规则：适合稳定的知识、流程和约束。
- 脚本或工具：适合机械、重复、可确定执行的操作。
- 工具选择规则：适合反复出现的依赖或方案选择问题。
- 项目文档更新：适合项目特有且需要长期保留的决策。
- 不沉淀：适合一次性问题，直接修复即可。

审查模型负责找问题，优化模型负责提出降低复发概率的方法，评估模块负责判断是否有效。三者不能互相替代。

### 4.4 效果评估

优化价值主要通过后续真实任务持续观察，而不是默认完整重放一次复杂开发现场。

核心指标包括：

- 任务成功率。
- 从首次执行到合格结果的返工轮数。
- 完成一次合格任务的总令牌和总耗时。
- 无效、重复的工具调用次数。
- 过程稳定性和同类问题复发率。
- 低成本模型加优化后，与高能力模型直接执行之间的差距。

只有高复用、高成本的优化，才考虑进入专门的 `Skill Benchmark`（技能基准测试）或 `A/B`（对照实验）。

### 4.5 团队管理层

当产品进入多人使用阶段，再增加云端实时采集、人员和项目权限、成本统计、审计记录、告警、任务状态和协作视图。

`Git`（版本控制）继续负责代码与版本历史；云端负责实时事件、统一索引、查询、权限和团队管理。两者互补，不互相替代。

### 4.6 算力执行层

算力执行层负责管理本地机器、`GPU`（图形处理器）、容器和任务，提供隔离执行、资源状态、排队调度、失败重试和结构化运行数据。

这一层优先复用 `Kubernetes`（容器调度平台）等成熟方案，只补工作台需要的任务编号、事件转换和数据接口。它是后期基础设施，不是产品核心，也不与团队管理层合并。

## 5. 当前代码现状

### 已经具备

- `Electron`（桌面应用框架）桌面端已经可以运行并选择项目。
- 能发现、索引和读取本地代码代理会话，并按会话工作目录筛选当前项目。
- 能按会话和轮次读取用户输入、回复、工具调用、工具结果、补丁、结束状态、耗时、令牌和原始文件位置。
- 已有时间线、历史会话选择、任务记录、流程文档生成和项目文档管理的基础实现。
- 已有统一事件时间线和第一版确定性结果审查，能够挂接原始记录、命令、文件变化、测试、模型令牌、上下文和结构化验证证据。
- 可以把选中轮次整理成任务流程文档，最近一次任务已验证这条链路基本可用。

### 仍处于过渡或测试状态

- 旧编辑器适配器、自定义观察注入和程序追踪已从桌面主流程移除，遗留包和旧测试素材仍待后续归档。
- 结果审查目前还没有任务级验证规范管理、审查发现跳回事件的交互和完整的 Playwright 证据文件管理。
- 流程文档生成已经可用，但标题提取、证据裁剪、失败状态和文档接续信息仍需稳定。
- 项目资料草稿、模型讨论和脚本草稿等界面属于试验功能，暂不据此扩大产品范围。
- 已具备同步包生成、`Sync`（同步）任务查看、项目仓库状态读取、整体拉取和确认式提交推送的基础流程；真实远程仓库和跨设备验收仍需补测。
- 三层审查、优化候选、效果评估、团队管理和算力执行尚未形成可用闭环。

## 6. 开发路线

### 第一阶段：代码代理专用的观察与跨设备接续

这是紧接当前代码现状的下一阶段。

1. 移除旧编辑器来源、自定义观察注入和双数据源在主流程中的依赖。
2. 直接、稳定、增量地解析代码代理会话事件文件，避免重复事件、历史重放和项目串线。
3. 统一项目、任务、会话、轮次、事件和证据的数据结构。
4. 补齐对话、工具、命令、文件变化、测试结果、耗时、令牌、状态和关键上下文引用。
5. 完善历史与实时观察，让实时模式只显示进入后新产生的活动，历史模式按轮次清楚分组。
6. 完善流程文档，使其能够承担新设备、新会话快速接续的主要作用。
7. 建立基于远程仓库的项目状态同步约定，并处理原始会话文件的隐私、体积和可选同步策略。

这一阶段完成的判断标准：用户能从一个真实任务看到可信时间线，生成可接续流程文档；在另一台设备拉取项目后，新会话可以依靠代码和文档继续工作，必要时还能回到原始事件证据。

### 第二阶段：结果审查与过程异常

先建立可解释的规则和结果证据，再逐步增加异常识别。重点验证提示是否准确、有用、可回溯，而不是追求异常数量。

### 第三阶段：独立审查与优化候选

引入独立高能力模型提出风险假设，再由优化模型生成技能、脚本、规则或文档候选。默认需要人工确认，不自动写入长期经验库。

### 第四阶段：长期效果评估

为优化项记录版本、适用范围、使用情况和后续任务指标，判断是否减少返工、令牌、耗时和高能力模型依赖。

### 第五阶段：团队管理

在真实出现多人实时协作需求后，建设云端采集、权限、成本、审计、告警与团队视图。

### 第六阶段：算力执行

在团队任务规模和本地算力需求明确后，接入容器、图形处理器与成熟调度平台，形成隔离、可调度的执行环境。

## 7. 当前明确不做

- 不再继续扩展旧编辑器观察能力。
- 不把跨设备恢复同一个代码代理会话作为目标。
- 不在个人阶段建设独立云服务和实时团队系统。
- 不从零实现容器或图形处理器调度平台。
- 不默认完整复现每次失败任务。
- 不自动把每个问题写成长期技能。
- 不把试验界面的功能数量作为产品进展。

## 8. 后续需要继续确认的产品决策

1. 原始会话事件文件默认不同步、选择性同步，还是脱敏后同步。
2. 一个任务是否允许跨多个会话，以及任务边界由用户选择还是自动识别。
3. 时间线默认显示全部事件还是只显示关键事件，详细证据如何展开。
4. 第一批结果证据优先支持测试、截图还是性能数据。
5. 流程文档的固定结构、自动生成时机和人工确认方式。
6. 哪些信号足以触发独立模型审查，避免高能力模型被低价值调用。
7. 优化候选如何审批、版本化、限定适用范围和回退。
8. 进入团队管理层与算力执行层的真实触发条件。

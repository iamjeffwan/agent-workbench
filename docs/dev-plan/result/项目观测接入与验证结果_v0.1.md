# 项目观测接入与验证结果 v0.1

## 1. 本次目标

将 `project-observation`（项目观测）包接入桌面端真实会话监听流程，并验证同一条 Codex 原始会话经过旧时间线与 `ObservationSession`（统一观测会话）后，能否得到一致的轮次状态、文件变化和环境变化。

本次不包含工作台页面展示、云同步和审查模型接入。

## 2. 已完成改动

### 2.1 桌面端项目观测服务

- 发现运行中的新轮次时保存项目的轮次前快照。
- 轮次结束时保存轮次后快照，并生成 `TurnDiff`（轮次差异）和环境变化。
- 观测结果保存在桌面应用用户数据目录，重复刷新不会重复计算。
- 应用重启后可以继续完成已经保存了前快照的轮次。
- 工作台在轮次结束后才开始监听时，明确标记为不可生成，不补造轮次前快照。
- 采集失败会保留错误阶段，后续刷新可以重试。
- 两次快照之间可能包含人工或其他进程的修改，因此当前归因标记为 `source_uncertain`（来源不确定）。

### 2.2 桌面端监听链路

- 桌面端刷新 Codex 会话时调用项目观测服务。
- 返回状态中增加项目观测摘要，并根据观测是否可用更新代码状态。
- 桌面端增加对 `project-observation`（项目观测）包的工作区依赖。

### 2.3 统一观测来源验证能力

- 项目观测服务同时支持旧时间线事件和 `ObservationSession`（统一观测会话）。
- 新增真实验证脚本，可并行读取同一份 Codex 原始会话，并对照：
  - 原始 `JSONL`（逐行 JSON 日志）；
  - 旧时间线事件；
  - `ObservationSession`（统一观测会话）；
  - 两条观测路径生成的文件变化与环境变化。

## 4. 真实 Codex 验证结果

### 4.1 实际执行

2026-08-19 启动了桌面应用自带的 `Codex CLI 0.148.0-alpha.15`（Codex 命令行工具），模型为 `gpt-5.6-sol`（GPT-5.6 编程模型），工作目录为独立临时 Git 项目。验证监听器成功发现了新会话，并开始同时读取旧时间线与 `ObservationSession`（统一观测会话）。

真实轮次计划创建三个文件：

- `codex-created.txt`（验证文件）；
- `package.json`（Node.js 项目清单）；
- `pnpm-lock.yaml`（pnpm 锁文件）。

这样可以同时验证普通文件变化和依赖环境变化。

### 4.2 结果

本次真实轮次未完成，不能判定文件差异和环境变化通过。

实际失败发生在模型开始执行前：`WebSocket`（网页套接字）请求连续 5 次超时，降级到 `HTTPS`（加密网页请求）后仍然超时。因此三个目标文件均未创建，也没有可用于最终对照的完整轮次。

本次已经确认：

- 桌面应用自带的真实 `Codex CLI`（Codex 命令行工具）能够启动；
- 新会话和真实轮次编号能够生成；
- 验证程序能够发现该会话并进入观测；
- 当前阻塞点是独立 CLI 进程到模型接口的网络连接，不是项目观测代码报错。

此前安装的 `Codex CLI 0.92.0`（Codex 命令行工具）也进行了同类尝试，同样在模型接口请求阶段超时。为排除证书读取问题，又使用 Git 自带证书链运行新版 CLI；GitHub 接口可以返回响应，但模型接口仍然超时。

因此，本次结果文档不把真实 `TurnDiff`（轮次差异）、环境变化及三种数据来源对照标记为通过。验证脚本已保留，网络链路恢复后可直接重新执行并生成完整 `result.json`（结果文件）。

## 5. 当前结论与限制

- 桌面端项目观测接入和自动测试已完成。
- 旧时间线与 `ObservationSession`（统一观测会话）的包级一致性测试已通过。
- 独立真实 Codex 轮次已启动并被监听，但模型网络超时，端到端结果仍待补齐。
- 如果工作台在轮次开始后才启动，无法准确重建轮次前状态。
- 观测窗口内的人工或外部进程修改暂时无法与智能体修改完全区分。
- 页面展示按当前产品调整安排暂缓。

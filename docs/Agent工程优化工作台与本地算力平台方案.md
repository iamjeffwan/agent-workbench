# Agent 工程优化工作台与本地算力平台方案

> 从执行可观测，到工程审查、经验沉淀与低成本模型增强
> 方案整理版 · 2026 年 8 月

## 1. 项目定位

工作台的核心不是“看日志”，也不是重新造一个算力平台，而是把真实开发中的 Agent 执行过程转化为**可观察、可诊断、可优化、可验证的工程经验**。

底层算力与 `Kubernetes`（容器编排平台）只负责提供稳定、隔离、可调度的执行环境。

### 1.1 真正要解决的问题

真实开发中，用户通常不会在 Agent 每次偏离时回滚重跑，而是直接要求它继续修改。

用户最容易感知的是结果：

- 功能不对；
- 速度慢；
- 页面难看；
- 返工多；
- 执行过程明显卡顿或反复试错。

但很多更深层的问题——架构选择、工具选择、耦合、复杂度、无效试错——用户未必有能力直接识别。

**核心矛盾是：Agent 的错误往往发生在过程里，但用户最容易看到的是结果。工作台的价值，是把“用户看得到的坏结果”与“过程里可能导致它的异常模式”建立联系。**

### 1.2 当前最值得保留的主线

1. 把 Agent 的对话、工具调用、文件修改、命令执行、耗时和关键上下文整理成统一的 `Timeline`（时间线）。
2. 自动发现结果层和过程层的异常，把深层工程问题转化为“有证据的风险提示”。
3. 让高能力模型负责审查和优化，而日常开发尽量由更便宜的执行模型完成。
4. 把反复出现且值得沉淀的问题，转化为 `Skill`（技能）、脚本或规则，再观察它是否减少返工、Token 与对强模型的依赖。

### 1.3 不应该成为核心的东西

- 不把“一键完整复现某次失败”当作默认能力。真实开发上下文很复杂，完整还原成本高，也不一定值得。
- 不把“生成更多 Skill”当成成功指标。一次性、过拟合、互相冲突的 Skill 反而会降低稳定性。
- 不从零重造 Kubernetes GPU 调度平台。底层基础设施优先复用成熟方案，只补工作台需要的接口。

## 2. 工作台整体功能结构

| 模块 | 主要输入 | 主要输出 | 价值 |
|---|---|---|---|
| 执行观察 | Agent 日志、JSON、工具调用、文件变更 | 统一 Timeline、关键事件、上下文引用 | 先把过程看清 |
| 三层审查 | 执行过程 + 最终结果 | 结果问题、过程异常、深层风险 | 把隐性问题显性化 |
| 优化生成 | 审查证据 + 项目上下文 | Skill / 脚本 / 规则候选 | 把经验固化 |
| 效果评估 | 后续真实任务 + 成本指标 | 成功率、返工、Token、稳定性 | 判断优化是否值得保留 |
| 团队执行层 | 本地机器、GPU、容器、任务 | 隔离执行、资源状态、结构化运行数据 | 支持规模化运行 |

## 3. 三层审查：从“看结果”到“发现深层风险”

### 3.1 第一层：结果审查

这一层最可靠，也最接近真实用户判断。重点不是理解 Agent 为什么这么做，而是判断做出来的东西到底好不好。

主要检查：

- 功能是否符合需求，测试是否通过；
- 响应速度、页面卡顿、关键任务耗时；
- 视觉效果是否接近要求；
- 可以接入 `Playwright`（浏览器自动化工具）等，让系统自动点击、测量、截图并形成结果证据。

### 3.2 第二层：过程指标审查

这一层把成熟软件工程经验转换成可自动识别的过程信号，不要求用户自己有很深的架构经验。

| 异常模式 | 可能意味着什么 | 可自动观测信号 |
|---|---|---|
| 长时间阻塞 | 方案选择不合适、依赖问题、调试路径过长 | 连续长耗时、无产出等待、反复超时 |
| 同一步骤反复调用 | Agent 对关键环节判断偏移 | 相同工具、命令或文件被高频重复访问 |
| 频繁返工 | 初始方案不稳或理解偏差 | 刚修改的文件短时间内被多次撤销或重写 |
| 重复造轮子 | 工具选择能力不足 | 已有成熟库或工具但仍反复自写基础实现 |
| 上下文膨胀 | 信息检索和聚焦能力下降 | 输入持续增长但有效输出下降 |

### 3.3 第三层：独立模型审查

这一层不要求用户先定义“什么是深层好设计”，而是由独立的高能力审查模型按固定工程维度提出**有证据的风险假设**。

主要维度包括：

- 架构合理性、模块边界与耦合；
- 复杂度、可维护性、可测试性；
- 错误处理、性能风险、安全风险；
- 工具与依赖选择是否合理。

**第三层不是判决器，而是“专家假设生成器”。** 每个结论都应尽量包含：证据、风险、影响、可验证建议。

---

## 4. 审查模型与优化模型分开

审查和优化最好不是同一个角色。让一个模型同时“找问题 + 证明自己方案正确”，容易形成自我确认。

| 角色 | 负责回答 | 不负责 |
|---|---|---|
| 审查模型 | 哪里可能有问题？证据是什么？影响是什么？ | 不直接宣布应该沉淀哪个 Skill |
| 优化模型 | 这个问题怎样降低复发概率？适合 Skill、脚本、规则还是不沉淀？ | 不直接宣布优化已经有效 |
| 评估模块 | 优化后是否降低返工、Token 与模型能力依赖？ | 不负责凭一次结果下结论 |

### 4.1 运行模型分层

更符合成本目标的方式，是让便宜模型长期执行，让顶级模型只在高价值节点介入。

- **执行模型**：优先使用成本更低的模型完成日常编码、修改、测试。
- **审查模型**：使用更强模型做结构化工程审查。
- **优化模型**：使用更强模型综合历史证据、工程规范与工具生态，生成候选 Skill、脚本或规则。

长期目标不是让弱模型“智商变高”，而是把强模型反复进行的检索、判断和试错固化为工程经验，让低成本模型在特定开发任务上更稳定、更少返工。

## 5. 上下文记录：不要事后猜，执行时主动留证

完整复现难，主要不是容器不够，而是很难知道模型当时究竟依赖了哪些上下文。

因此更实用的是，在执行过程中主动记录“关键决策依据”。

### 5.1 建议记录的关键证据包

- 当前任务目标，以及进入关键决策前的局部上下文摘要；
- 引用过的文件、代码片段、网页、工具输出和版本信息；
- 关键方案选择：选择了什么、主要依据是什么、放弃了哪些明显替代方案；
- 执行后的结果：测试、截图、错误、性能数据、返工次数；
- 资源与成本：Token、模型、耗时、工具调用次数。

这里不要求模型暴露完整内部推理，只需要结构化输出**引用来源和决策依据摘要**，方便后续审查和对照。

## 6. 优化沉淀：什么时候值得生成 Skill

普通一次性错误，继续让 Agent 修掉通常最便宜。只有具有复用价值的问题，才值得进入沉淀流程。

比较适合沉淀的情况：

- 同类问题反复出现；
- 每次出现都会造成明显 Token、时间或返工成本；
- 问题能够抽象成稳定的操作流程、工具选择或约束；
- 优化后可以在后续任务里自然观察效果。

### 6.1 沉淀形式不要只有 Skill

| 问题类型 | 优先沉淀形式 | 例子 |
|---|---|---|
| 知识 / 流程偏差 | Skill / 规则 | 遇到某类任务先查哪些资料、按什么顺序验证 |
| 机械重复操作 | 脚本 / 工具 | 固定格式转换、环境检查、批量验证 |
| 工具选择错误 | 规则 + 工具白名单 | 优先使用成熟公开库，不重复自造基础能力 |
| 一次性特殊问题 | 不沉淀 | 直接修复，避免污染长期经验库 |

## 7. 效果验证：从“复现失败”改成“证明长期价值”

完整复现原始开发现场既昂贵又不稳定，因此验证重点应从“这一次能不能重放”转向：

**这个优化是否持续降低完成合格任务的成本。**

### 7.1 核心指标

- 任务成功率：完成需求并通过必要检查的比例；
- 返工次数：从首次执行到达到可接受结果需要多少轮；
- 完成一次合格任务的总 Token，而不是单次调用 Token；
- 总耗时与无效工具调用次数；
- 低成本模型 + Skill 与强模型裸跑之间的差距。

最值得长期追的指标是：

> **Skill 有没有降低模型对“能力”和 Token 的依赖。**
>
> 换句话说：更便宜的模型能否因为经验沉淀而稳定完成原本需要更强模型才能完成的任务。

### 7.2 验证策略

- 默认不为每一个优化专门做昂贵的多轮 A/B 测试；
- 优先观察后续真实任务：是否更少返工、更少重复搜索、更少重复造轮子；
- 对于高复用、高成本的 Skill，再进入专门的 `Skill Benchmark`（技能基准测试）；
- 基准测试尽量固定代码快照、任务、允许上下文、工具权限和模型版本；必要时重复多次看波动，而不是相信单次结果。

## 8. Kubernetes 与本地算力平台：作为执行层，而不是产品核心

团队版可以把公司或实验室现有的 GPU 机器组成一个**本地优先的小型分布式算力池**。

这个方向本身已有大量成熟基础设施，因此不建议重新实现底层调度，而是复用现有方案并对接工作台。

### 8.1 Kubernetes 真正负责什么

- 管理多台执行机器和容器生命周期；
- 根据 CPU、GPU、显存等资源把任务调度到合适节点；
- 处理任务排队、失败重试、节点掉线、资源限制和隔离；
- 为 Agent 实验提供一致、可控制的执行环境。

### 8.2 工作台需要补的接口

- 统一任务 ID，把算力任务与工作台 Timeline 对齐；
- 采集模型调用、工具调用、日志、错误、资源消耗与任务状态；
- 将底层执行记录转成工作台统一的结构化事件，而不是直接暴露 Kubernetes 原始对象；
- 保留容器镜像、代码版本、模型配置等实验元信息，为必要的局部重放或回归验证提供条件。

### 8.3 Kubernetes 的学习方式

先用成熟方案把真实任务跑起来，再顺着实际问题学习 `Pod`（运行实例）、`Job`（一次性任务）、调度、资源限制、故障恢复和 GPU 管理；最后只补项目真正需要的接口。

这样学到的是“为什么需要”和“实际怎么用”，而不是单纯记配置。

## 9. 推荐的整体架构

| 层级 | 职责 |
|---|---|
| 用户 / 团队 | 提交开发任务，查看结果、异常、优化建议和经验效果 |
| Agent 执行层 | 低成本模型执行开发任务，主动输出关键上下文引用和决策依据摘要 |
| 工作台采集层 | 解析 JSON、tracing、工具调用、文件变更，生成统一 Timeline |
| 审查层 | 结果审查 + 过程指标 + 独立强模型审查 |
| 优化层 | 强模型生成 Skill、脚本、规则候选，并管理版本与适用范围 |
| 评估层 | 持续记录成功率、返工、Token、耗时和弱模型稳定性 |
| 算力执行层 | Kubernetes + 容器 + GPU 调度，提供团队级隔离与资源管理 |

整体链路可以概括为：

```text
真实开发任务
    ↓
低成本 Agent 执行
    ↓
Timeline + 关键上下文 + 结果证据
    ↓
结果审查 → 过程异常 → 独立模型深层审查
    ↓
优化模型生成候选方案
    ↓
Skill / 脚本 / 规则
    ↓
后续真实任务持续观察
    ↓
保留有效经验，淘汰无效经验
```

团队版底层可以进一步接入：

```text
团队机器 / GPU
      ↓
Kubernetes / 成熟 GPU 调度方案
      ↓
隔离 Agent 任务
      ↓
结构化执行数据
      ↓
Agent 工程优化工作台
```

## 10. 建议的开发优先级

为了避免项目再次发散，建议按“先形成可用闭环，再扩展基础设施”的顺序推进。

### 第一阶段

把 Codex 等现有执行日志稳定整理成 Timeline，并补齐关键上下文引用、工具调用、文件变化、耗时和结果证据。

### 第二阶段

做好结果审查和过程异常识别，让工作台从“看见”升级到“发现问题”。

### 第三阶段

加入独立审查模型和优化模型，先输出候选方案，不急着自动写入长期 Skill。

### 第四阶段

建立 Skill 版本、适用范围和效果指标，开始观察“低成本模型 + Skill”是否减少返工和 Token。

### 第五阶段

团队版接入 Kubernetes / GPU 执行层，把不同人的 Agent 任务统一采集进工作台。

---

## 11. 当前最需要警惕的风险

- 把工作台做成“功能大全”，导致 Timeline、审查、优化、算力每块都不够深；
- 审查模型输出大量听起来专业但缺乏证据的建议，最终变成新的噪声源；
- Skill 过度沉淀，形成规则冲突和任务过拟合；
- 为了证明优化有效而设计过重的复现实验，最后测试成本高于实际节省的成本；
- 把 Kubernetes 当成亮点而不是基础设施，开发时间被底层运维问题吞掉。

---

## 12. 最终定位

**一个面向真实软件开发的 Agent 工程优化工作台：持续观察 Agent 如何完成任务，自动发现结果与过程中的问题，用高能力模型提炼可复用工程经验，并验证这些经验能否让更便宜的模型以更低 Token、更少返工完成同类工作。**

`Kubernetes`（容器编排平台）与本地算力平台是团队版的执行基础：负责把分散的机器和 GPU 组织成稳定、隔离、可调度的任务环境，并把结构化运行数据输送给工作台。

它有实际价值，但不应取代“Agent 观察、诊断、优化与经验验证”这一核心。
